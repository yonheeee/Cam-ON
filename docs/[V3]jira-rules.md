## 1. 제목 태그 형식 (필수)

```
[에픽코드-파트코드] 이슈 제목
```

### 태그 검증 규칙

- 앞자리는 **반드시 아래 에픽 코드표에 있는 값**, 뒷자리는 **반드시 아래 파트 코드표에 있는 값**을 쓴다.
- 둘 중 하나라도 표에 없으면 **이슈를 만들지 않고 먼저 사용자에게 확인한다.** 임의로 새 코드를 만들지 않는다.
- 태그 없이 이슈를 만들지 않는다.


### 파트 코드

| 코드 | 의미 |
|---|---|
| FE | 프론트엔드 |
| BE | 백엔드 |
| AI | AI/모델 |
| PLAN | 기획/문서/의사결정 |
| PM | 행정/일정 관리 |
| QA | 테스트/검증 |
| DESIGN | UI/UX 디자인 |

### 에픽 코드

에픽은 **두 계열**로 나뉜다. 이 구분이 "이걸 어느 에픽에 넣나"의 판단 기준이다.

#### (A) 기능(산출물) 에픽 — **버그는 반드시 이 계열로 들어간다**

| 코드 | 에픽 키 | 에픽명 |
|---|---|---|
| ACC | S15P11B110-11 | 계정/세션/DB |
| LOBBY | S15P11B110-82 | 대기방 |
| CAM | S15P11B110-13 | 카메라/준비상태 |
| NET | S15P11B110-15 | 재접속/네트워크 |
| SCORE | S15P11B110-19 | 종합점수 |
| G01 | S15P11B110-16 | 게임-엄마! 내 물건 어딨어? |
| G02 | S15P11B110-17 | 게임-손은 눈보다 빠르다 |
| G03 | S15P11B110-18 | 게임-말하지 않아도 알아요 |

> 게임 3종의 이름은 2026-07-28 「Cam, On! 서비스 기획 확정」 기준이다.
> 구 이름(물건가져오기 / 닌자 / 몸으로 말해요)은 사용하지 않는다.

#### (B) 범활동 에픽 — 어느 기능에도 귀속되지 않는 활동

| 코드 | 에픽 키 | 에픽명 |
|---|---|---|
| DOC | S15P11B110-1 | 기획 |
| ADMIN | S15P11B110-2 | 사무 |
| TEST | S15P11B110-23 | 테스트 |
| DESIGN | S15P11B110-64 | UI/UX 디자인 |
| SOUND | S15P11B110-97 | 사운드 |
| PRESENT | S15P11B110-85 | 발표 준비 |
| VID | S15P11B110-86 | 영상 포트폴리오 제작 |
| DEPLOY | S15P11B110-168 | CI/CD |
| MERGE | S15P11B110-184 | 브랜치 통합 |

> 코드와 에픽명이 다른 것은 정상이다 (LOBBY=대기방, ACC=계정/세션/DB, VID=영상 포트폴리오 제작 등).

#### 빈 에픽 (사용 금지)

> ⚠️ `S15P11B110-12`(방/방장), `S15P11B110-14`(방 설정)는 대기방(82)으로 통합되어 하위 이슈가 없는 빈 에픽으로 남아 있다. 삭제되지 않았으니 **새 이슈를 여기 만들지 말 것.**

#### 새 에픽이 필요할 때

1. **기능 에픽을 우선 검토한다.** 사용자가 인지하는 기능 영역인가?
2. 여러 기능에 걸치고 어느 기능의 산출물도 아닐 때만 **범활동 에픽**으로 만든다.
3. 어느 쪽인지 확실하지 않으면 **에픽을 만들지 않고 사용자에게 확인한다.**

## 2. 이슈 타입 구분

| 타입 | 정의 | 판단법 |
|---|---|---|
| **스토리** | 플레이어/사용자 관점의 기능 단위 | "플레이어는 ~할 수 있다"로 자연스럽게 말이 되면 스토리 |
| **작업** | 스토리를 구현하기 위한 개발자 관점 작업 (연동, 정리, 인프라, 데이터 수집, 문서화, QA 등) | 유저는 존재 여부를 모름 |
| **버그** | **이미 구현된 기능이 명세대로 동작하지 않는 것** | 고쳐야 할 결함이면 버그 |

- 판단이 애매하면 기본값은 **작업**으로 만들고 사용자에게 확인한다.
- 통합/머지 작업처럼 개발자 관점 작업은 스토리가 아니라 **작업**이다.

### 버그 규칙

1. **버그는 스토리로 감싸지 않는다.** 버그 하나가 그 자체로 완결된 작업 단위다.
2. **버그의 에픽은 "발생한 화면"이 아니라 "원인이 있는 기능 영역"이다.** 게임 중에 발생했어도 원인이 대기방/카메라/네트워크에 있으면 그 에픽으로 간다.

실제 판정 사례:

| 이슈 | 현상 | 에픽 | 이유 |
|---|---|---|---|
| -169 | 전원 준비 완료 전에 게임이 시작됨 | **CAM** | 준비 상태 판정 로직의 문제 |
| -170 | 게임 시작 시 일부 참가자가 화면 이동 못함 | **LOBBY** | 대기방→게임 전환의 문제 |
| -171 | 게임 중인 방에 입장이 차단 안 됨 | **LOBBY** | 방 입장 판정의 문제 |
| -179 | 대기방에서 방장이 나가면 위임이 안 됨 | **LOBBY** | 대기방 방장 관리의 문제 |
| -180 | 게임 중 나가면 검은 화면으로 남음 | **NET** | 이탈/재접속 처리의 문제 |

3. **버그를 TEST 에픽에 모으지 않는다.** 모으면 "기능별로 얼마나 튼튼한가"를 볼 수 없게 된다. QA 발견 버그만 따로 보려면 에픽이 아니라 **라벨**(7번)을 쓴다.

## 3. 이슈 연결

### 에픽 연결 (필수)

- **모든 이슈는 생성 시점에 에픽(parent)을 지정한다.** 비워둔 채 생성하지 않는다.
- 에픽에 연결되지 않은 이슈는 어느 에픽 화면에도 나타나지 않아 사실상 보이지 않는 이슈가 된다.
- Jira API에서는 생성 후 별도 편집이 필요하다 (부록 참고).

## 4. 생성 시점 필수 필드

아래 5개는 **이슈를 만드는 시점에 반드시 채운다.** 하나라도 없으면 **생성하지 않고 사용자에게 먼저 확인한다.**

| 필드 | 규칙 | 상세 |
|---|---|---|
| 제목 태그 | 에픽 코드 + 파트 코드 | 1번 |
| 이슈 타입 | 스토리 / 작업 / 버그 | 2번 |
| 에픽(parent) | 필수 | 3번 |
| 담당자 | 필수 | 9번 |
| Story Points | 필수, 최대 3 | 5번 |
| 우선순위 | 필수 (2026-07-30부터) | 6번 |

---

## 5. Story Points

- 필드: **Story Points** (`customfield_10031`)
- **SP = 이 작업을 하는 데 실제로 걸리는 시간(시간 단위, 정수).** 피보나치 추정이 아니라 그냥 예상 소요 시간이다.
- **최대 3을 넘지 않는다.** 3시간을 넘어갈 것 같은 작업은 만들 때부터 더 작은 단위로 쪼갠다.
- **Description에 "난이도 / 예상 소요 시간 / Story Points"를 따로 적지 않는다.** SP 필드 하나만 쓴다. (과거 -164, -161, -159에서 3중 표기가 발생했고, -164는 SP 4로 상한도 위반했다.)

---

## 6. 우선순위 (2026-07-30 신설)

**2026-07-30부터 생성되는 모든 이슈에 우선순위를 지정한다.** 그 이전 이슈는 소급 변경하지 않는다.

| 값 | 기준 |
|---|---|
| **Highest** | 시연 시나리오를 **끝까지 진행할 수 없게** 만드는 것 (블로커) |
| **High** | 시연 화면에 보이지만 진행은 되는 것 |
| **Low** | 위 둘이 아닌 전부 (기본값) |

- **Medium / Lowest는 사용하지 않는다.** 애매한 칸을 없애야 실제로 운영된다.
- 별도의 트리아지 회의는 두지 않는다. **이슈를 만드는 사람이 만드는 시점에 정한다.** 그래서 기준을 위와 같이 객관적으로 못박아 둔다.
- 판정 근거는 SSAFY QA 공지의 "핵심 기능이 잘 안되면 큰 감점, 레이아웃 깨지는 건 덜 감점"이다.

## 7. 라벨

**`qa` 하나만 사용한다.**

- 대상: QA(내부 테스트, 베타 테스트, 사전 Q/A, 코치·컨설턴트 Q/A) 과정에서 **발견된 버그**
- 목적: "QA에서 n건 발견 → m건 수정"이라는 숫자를 발표 자료에 쓰기 위함. 에픽을 뷰로 쓰지 않고도 QA 발견 버그만 필터링할 수 있게 하는 장치다.
- 다른 라벨은 임의로 추가하지 않는다.

## 9. 담당자 (필수)

- **담당자는 이슈를 만드는 시점에 반드시 지정한다. 비워둔 채 생성하지 않는다.**
- 사용자가 담당자를 말하지 않았다면, 만들기 전에 누구 담당인지 먼저 물어본다.
- **상태를 "진행 중"으로 전환할 때도 담당자가 비어 있으면 전환하지 않는다.**

## 10. 스프린트 운영 리듬

- 스프린트는 매주 월요일 9시 이후 팀장이 시작한다 (백로그 → 이번 주 스프린트로 이슈를 옮긴 뒤).
- 매일 아침 스크럼에서 그날 할 일을 말한 직후 바로 Jira에 이슈로 추가하는 방식이 기본 흐름이다.
- **생각날 때마다 즉흥적으로 이슈를 추가하는 것은 지양한다.** 가능하면 백로그에 할 일을 미리 적어두고, 스크럼/스프린트 계획 시점에 꺼내 쓴다. 사용자가 "지금 갑자기 생각난 걸 추가해달라"고 명시적으로 요청한 경우가 아니면, 이런 애드혹 추가가 맞는지 한 번 확인한다.
- **예외**: QA 과정에서 발견된 버그는 발견 즉시 이슈로 만든다. 애드혹 지양 규칙을 적용하지 않는다.

## 11. 에이전트가 지켜야 할 것

### 생성 전
1. **중복 검색을 먼저 한다.** 유사한 이슈가 이미 있는지 JQL로 확인하고, 있으면 새로 만들지 않고 사용자에게 알린다.
2. 에픽 코드 / 파트 코드를 임의로 새로 만들지 않는다.
3. 이슈 타입(스토리/작업/버그)을 임의로 정하지 말고 애매하면 사용자에게 확인한다.
4. 여러 건을 한 번에 만들 때는 먼저 목록을 보여주고 확인받은 뒤 생성한다.
5. **4번의 필수 필드 중 하나라도 확정되지 않았으면 생성하지 않고 확인한다.**

### 작업 중
6. 규칙 위반, 모호한 지점, 누락된 필드를 **발견하는 즉시 사용자에게 알린다.** 이미 명확한 맥락을 재확인하지는 않는다.
7. **한글 필드 값은 유니코드 이스케이프 없이 그대로 전송한다.** (2026-07-30 에픽명을 이스케이프로 보내 문자가 깨진 사고가 있었다.)
8. 사용자가 지시한 범위를 넘지 않는다. "완료된 이슈 찾기"는 "새 이슈 만들기"가 아니고, "설계"는 "구현 변경"이 아니다.

### 종료 시
9. 그 세션에서 **생성·수정한 이슈 키 목록을 요약해 보고한다.**
