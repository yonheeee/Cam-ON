## 2. 이슈 타입 구분

- **스토리**: 플레이어/사용자가 "무엇을 할 수 있는가"를 설명. "플레이어는 ~할 수 있다"로 자연스럽게 말이 되면 스토리.
- **작업**: 스토리를 구현하기 위한 개발자 관점 작업(연동, 정리, 인프라, 데이터 수집, QA 등). 유저는 존재 여부를 모름.
- 판단이 애매하면 기본값은 **작업**으로 만들고 사용자에게 확인한다.

## 3. 스토리-작업 연결

- **이 프로젝트는 클래식(company-managed) 프로젝트라 스토리를 작업의 부모로 지정할 수 없다.** (Jira API 제약, 계층 변경 불가)
- 대신 스토리와 관련 작업은 **"Relates" 링크**로 연결한다.
- 작업만 단독으로 만들어도 되지만(스토리 없이), 가능하면 관련 스토리에 링크해둔다.
- 스토리 상태는 자동 동기화되지 않는다 (Automation 규칙 미완성 상태 — 수동으로 갱신).

## 4. Story Points

- 필드: **Story Points** (`customfield_10031`)
- **SP = 이 작업을 하는 데 실제로 걸리는 시간(시간 단위, 정수).** 피보나치 추정이 아니라 그냥 예상 소요 시간이다.
- **최대 3을 넘지 않는다.** 3시간을 넘어갈 것 같은 작업은 만들 때부터 더 작은 단위로 쪼갠다.
- 이슈를 만들 때(진행 중으로 전환하기 전이 아니라 **생성 시점**) 바로 값을 설정한다.

### 스프린트 가동률 기준
- 스프린트 = 1주 단위. 팀원 1인당 가용 시간 = 8시간 × 5일 = **40시간 = 40 SP**.
- 한 스프린트가 끝났을 때 팀원의 SP 합계가 **40 미만이면 안 된다** (집 가서 한 개발 포함).
- 이슈를 만드는 AI 에이전트는 이 기준을 참고해서, 한 사람에게 배정된 스토리 포인트 합이 비정상적으로 낮거나 높으면 사용자에게 알려준다.

```
## 완료 기준

- [ ]
```

## 6. 담당자 (필수)

- **담당자는 이슈를 만드는 시점에 반드시 지정한다. 비워둔 채로 생성하지 않는다.**
- 사용자가 담당자를 말하지 않았다면, 만들기 전에 누구 담당인지 먼저 물어본다.
- **상태를 "진행 중"으로 전환할 때도 담당자가 비어있으면 전환하지 않는다.** 담당자 없는 이슈를 진행 중으로 바꿔달라는 요청을 받으면, 먼저 담당자를 지정해야 한다고 안내한다.

## 7. 스프린트 운영 리듬

- 스프린트는 매주 월요일 9시 이후 팀장이 시작한다 (백로그 → 이번 주 스프린트로 이슈를 옮긴 뒤).
- 매일 아침 스크럼에서 그날 할 일을 말한 직후 바로 Jira에 이슈로 추가하는 방식이 기본 흐름이다.
- **생각날 때마다 즉흥적으로 이슈를 추가하는 것은 지양한다.** 가능하면 백로그에 할 일을 미리 적어두고, 스크럼/스프린트 계획 시점에 꺼내 쓰는 방식을 우선한다. 사용자가 "지금 갑자기 생각난 걸 추가해달라"고 명시적으로 요청한 경우가 아니면, 이런 애드혹 추가가 맞는지 한 번 확인한다.

## 8. 에이전트가 지켜야 할 것

- 에픽 코드/파트 코드를 임의로 새로 만들지 않는다.
- 이슈 타입(스토리/작업)을 임의로 정하지 말고 애매하면 사용자에게 확인한다.
- 여러 건을 한 번에 만들 때는 먼저 목록을 보여주고 확인받은 뒤 생성한다.
- 담당자, Story Points는 생성 시점에 반드시 채운다 (7번 참고).
