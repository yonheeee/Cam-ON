System Architecture

Cam-ON — 시스템 아키텍처

Frontend가 AI 서버와 Spring 서버를 각각 직접 호출하며 중간에서 데이터를 이어준다. AI 서버는 손동작/객체 인식만 하고 게임 상태는 모르며, Spring 서버는 게임 상태만 관리하고 인식 로직은 모른다 — 두 서버는 서로 직접 통신하지 않는다. 모든 필드가 카드에 바로 보이고, 연결선은 평소엔 숨어있다가 마우스를 올리거나 클릭한 카드의 관계만 나타난다. 다이어그램 위에서 Ctrl(또는 ⌘)+스크롤(트랙패드 핀치도 가능)로 확대/축소.

AI 서버 Spring 서버 MySQL Redis 호출 / 데이터 흐름 확대 100%

Client

CLIENT

Frontend

참가자 화면 (브라우저)

  • 방 생성/입장, 카메라·마이크 권한, 준비 상태 체크
  • 참가자 간 화상통화 (WebRTC — 이 다이어그램엔 별도로 안 그림)
  • AI 서버에 인식 요청(프레임/랜드마크) 보내고 판정 응답 받기
  • Spring 서버와 STOMP로 방/게임 상태 실시간 동기화
  • AI 판정 결과를 Spring에 전달해 Redis에 반영되게 함 — 두 서버 사이 유일한 다리

Backend

AI

AI 서버

손동작·객체 인식 (Python)

  • MediaPipe로 랜드마크 추출 → 분류기로 판정
  • 물건 인식은 순수 분류만 하고 정답 여부는 모름, 손동작은 콤보 완성 여부까지 판정
  • detected_value/confidence(물건 가져오기), 완성된 스킬(손동작 스킬 배틀)을 Frontend에 응답

게임 로직·방 상태는 전혀 모름. 상태 없는(stateless) 순수 추론 서비스. MySQL도 직접 조회하지 않음 — 미션/제시어는 Spring이 관리.

APP

Spring 서버

게임 로직 · 상태 관리 (Java)

  • 방 생성/입장/퇴장, 방장 위임, 준비 상태 판정
  • STOMP로 참가자에게 실시간 상태 브로드캐스트
  • Redis 읽기/쓰기 (room/session/round/results 등), MySQL games/missions 조회
  • 물건가져오기·몸으로말해요는 제출값을 직접 판정, 손동작 스킬 배틀은 Frontend가 중계한 AI 판정 결과를 라운드 결과에 반영

인식 로직엔 관여 안 함(원본 이미지·좌표는 AI가 처리). AI 서버를 직접 호출하지 않음.

데이터 구조 상세

위 다이어그램의 MySQL·Redis 박스를 확대한 버전. 정적 참조 데이터(게임 종류·미션)는 MySQL에, 방이 열려있는 동안만 존재하는 데이터(방·참가자·세션·라운드)는 Redis에 둔다. 닌자·물건가져오기·몸으로말해요 세 게임은 공통 골격을 공유하고, 게임별로 다른 부분만 전용 구조를 따로 둔다.

게임 종류 자체에 대한 정의/설명 카탈로그다 — 특정 방에서 몇 번째로 어떤 게임을 하는지(순서)는 이 테이블이 아니라 room:{code}:course:{idx}가 담당한다. name 하나로 식별자와 표시값을 겸하므로(예: "NINJA") 값이 바뀌면 이 이름에 의존하는 로직도 함께 깨진다는 점은 감수. is_active는 삭제 대신 두는 노출 토글이다 — 0이면 대기방 코스 설정 화면의 선택 목록에서만 빠지고(=지금 체험 불가), row 자체는 남는다. 이미 만들어진 방의 course/session이 game_id를 값으로만(DB 제약 없이) 참조하고 있어서, row를 진짜로 지우면 그 참조가 끊기기 때문. min_rounds가 NULL이면 "참여자 수"로 앱이 계산(물건가져오기).

이 테이블은 Spring만 조회한다 — AI 서버는 stateless라 missions에 직접 접근하지 않고, 정답 판정은 전부 Spring이 한다. OBJECT(물건가져오기)는 Spring이 target_label을 AI가 응답한 detected_value와 비교해서 판정, CHARADES(몸으로말해요)는 AI 인식 자체가 없어 Spring이 keyword를 채팅과 문자열 비교. HAND_POSE(닌자)는 실제 콤보 판정엔 안 쓰이고 skill_gesture 쪽 데이터가 그 역할을 대신함(아래 skill_gesture 카드 참고) — 남아있지만 용도가 애매한 타입. round:{n}이 mission_id로 참조.

room:{code}

방 하나 = 키 하나

room_code로 정확히 1개 조회 (GET room:ABC123). 대기방에서 방장이 코스를 확정하면 course_length가 정해짐. 한 게임이 끝나면 current_session_seq를 1 증가시켜 course의 다음 항목으로 세션을 새로 만듦 — course_length에 도달하면 종합 결과로 이동. 방 종료 시 관련 키 전부 삭제.

HASH

room:{code}:course:{idx}

코스 한 칸 = 이 자리에 놓인 게임 + 라운드 수

game_idMySQL games 참조
round_count이 게임에 배정된 라운드 수

idx는 1..course_length. 대기방(COM05_CONFIG01)에서 방장이 게임 목록과 순서, 게임별 라운드 수를 한 번에 정하면 이 개수만큼 키가 만들어짐 — round:{n} 패턴처럼 "몇 번째"를 키 이름에 그대로 박아서 순서를 표현. 세션이 시작될 때 session:{seq}가 course:{seq}를 읽어 game_id/round_count를 그대로 가져다 씀. round_count는 games.min_rounds~max_rounds 범위 안에서만 설정 가능(애플리케이션이 검증).

SET

room:{code}:participants

참가자 토큰 멤버십(순서 없음)

memberguest token

"이 방에 누가 있는지" 확인/순회용. 입장 순서는 각 participant:{token}.joined_at을 읽어 정렬해서 구함 — 인원이 최대 4명이라 정렬 비용은 무시 가능(별도 ZSET을 유지할 만큼의 이득이 없음). 방장 재접속 유예 초과 시 이 순서대로 다음 참가자에게 연쇄 위임.

HASH

room:{code}:participant:{token}

참가자 1명 = 키 하나

nickname표시 닉네임
connection_status연결 상태
ready준비 완료 여부

ready는 "카메라 권한 완료 AND 인식 테스트 통과" 둘 다 만족해야 true. 전원 ready=true여야 게임 시작 가능. 닉네임 등록 시 이 방의 nicknames SET에 반영, 하트비트로 TTL 키 갱신.

HASH

room:{code}:session:{seq}

이 방의 진행 중인 게임

game_idcourse:{seq}에서 그대로 복사
total_roundscourse:{seq}.round_count에서 그대로 복사
current_round현재 라운드 번호

seq는 이 방에서 몇 번째 게임인지(room:{code}.current_session_seq와 동일 값, course의 위치와 1:1 대응). 이전엔 방장이 그때그때 "다른 게임"을 골라 세션을 만들었지만, 이제는 코스가 대기방에서 미리 확정되므로 game_id/total_rounds를 course:{seq}에서 그대로 복사해와 세션을 엶. 별도 status 없이 이 키의 존재 자체가 "세션 진행 중"이고, current_round가 total_rounds에 도달하면 이 세션 종료 → current_session_seq 증가. game_id는 값으로만 저장 — 존재 검증은 애플리케이션이 담당.

HASH

...:session:{seq}:round:{n}

라운드 하나 = 키 하나

mission_idMySQL missions 참조 (물건가져오기·몸으로말해요만 사용)
skill_idMySQL skill 참조, 이번 라운드 요구 콤보 (닌자만 사용)
presenter_token출제자 (몸으로말해요만 사용)
started_at시작 시각
closed라운드 종료 사유, "TARGET"|"TIMEOUT" (닌자만 사용)

n은 라운드 번호. 별도 status 없음 — 이 키의 존재 자체가 "라운드 진행 중"이고, results 키가 생기면 "종료"다. 출제자 연결 끊김(몸으로말해요)도 여기에 상태를 따로 두지 않고, presenter_token으로 room:{code}:participant:{token}의 connection_status를 조회해서 판단한다. 닌자의 skill_id는 session:{seq}:skill_order(아래 카드 참고)에서 라운드 번호로 가져온 값을 그대로 복사해온 것. closed는 "대상 지정 완료"와 "제한시간 타임아웃"이 동시에 라운드를 끝내려는 경합을 HSETNX(먼저 쓰는 쪽만 성공)로 막는 락 — 둘 중 이미 닫은 쪽이 있으면 나머지는 아무 것도 안 함. 콤보 자체(몇 단계짜리 시퀀스인지, 지금 몇 번째 단계까지 완성했는지)는 AI/프론트가 들고 있고 Spring은 완성된 순간의 skill_id 하나만 받는다.

하트비트는 클라이언트가 몇 초마다 "저 아직 살아있어요"를 서버에 보내는 신호다. 받을 때마다 이 키의 TTL을 15초로 다시 채운다. 신호가 끊기면 15초 뒤 키가 저절로 사라지고, 그 순간을 "이 사람이 진짜 나갔다"는 판정으로 쓴다 — 네트워크가 끊긴 걸 서버가 스스로 알아채긴 어렵기 때문.
